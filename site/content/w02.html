第 1 週你一次改一個常數、手動跑、手動比較。這樣做五次還行，做五十次就會出錯：忘了改回來、不記得這張圖是哪組參數跑的、新舊結果混在一起。

為什麼要學這個

職缺說「系統性的控制變數，結果不如預期就砍掉換方向」。前提是「改一個參數、看結果」這件事要便宜而且不出錯。這週做的「用參數呼叫程式、批次執行、自動彙整」，也是之後排程、容器、API、MLOps 的共同起點：它們本質上都是用參數執行一支程式，再檢查結束碼與輸出檔。

這週在大圖裡屬於「ETL」與「部署與排程」兩格的最小版本。範例：week02/tide_cli.py（一次實驗）、week02/batch.py（一整組實驗）。

一理論與示範

要讓實驗便宜又不出錯，需要四個觀念：用參數呼叫程式、用結束碼回報成敗、批次要能安全地重跑、用小工具快速檢查大量輸出。

Day 11. 一次執行＝一次實驗：參數與結束碼

argparse 把命令列上的文字轉成程式裡的變數，每個參數有型別、預設值與說明，--help 會列出全部。參數不合理時，程式要明確失敗，而不是硬算出一個怪結果。

week02/tide_cli.py（節錄）
p.add_argument("--s2-amp", type=float, default=0.45, help="S2 振幅 [m]")
p.add_argument("--freq", default="h", help='取樣頻率，如 "h"、"30min"')
p.add_argument("--out", required=True, help="輸出資料夾")

errors = validate(a)
if errors:
    for e in errors:
        print(f"參數錯誤：{e}", file=sys.stderr)   # 錯誤寫到 stderr
    return 2                                      # 非 0 = 失敗
名詞：結束碼（exit code）

程式結束時回報的數字。0 是成功，非 0 是失敗，慣例上 2 代表參數用錯。批次系統、排程器、CI 只看這個數字，不會讀你印出來的文字。

輸出給誰看本範例放什麼
stdout下一個程式一行 JSON 結果
stderr人錯誤訊息
結束碼呼叫它的程式0 成功、2 參數錯誤
輸出資料夾三個月後的你config.json、metrics.json、eta.csv
示範

python tide_cli.py --s2-amp -1 --out runs/bad 會印出「參數錯誤：振幅不能是負數」，接著 echo $?（PowerShell：$LASTEXITCODE）得到 2，而且不會建立 runs/bad。

tide_cli.py 從時間軸算實際經過的小時數，並用結束時間決定筆數，不再寫死 days * 24。打開下方的「用實際小時數」，兩種頻率都會落在真實曲線上。

time = pd.date_range(start=a.start, end=pd.Timestamp(a.start) + pd.Timedelta(days=a.days),
                     freq=a.freq, inclusive="left")
t_hours = (time - time[0]) / pd.Timedelta(hours=1)

--freq h 得到 1440 筆、最大潮差 3.00 m；--freq 30min 得到 2880 筆、最大潮差 3.03 m。筆數剛好兩倍，潮差接近，差異來自雜訊。修正成立。

Day 33. 批次的四個步驟，以及為什麼要能安全重跑

batch.py 做四件事：定義參數網格、每組送出一個工作並檢查結束碼、跳過已完成的、讀回所有結果彙整成 summary.csv。按「執行」看一次，再按一次看第二次有什麼不同。

week02/batch.py
GRID = {
    "s2_amp": [0.20, 0.45, 0.70, 0.90, 1.00],
    "seed": [1, 2],
}

def already_done(folder: Path, params: dict) -> bool:
    cfg, met = folder / "config.json", folder / "metrics.json"
    if not (cfg.exists() and met.exists()):
        return False
    old = json.loads(cfg.read_text(encoding="utf-8"))
    return all(old.get(k) == v for k, v in params.items())
名詞：冪等性（idempotency）

做一次或做很多次，結果都一樣。批次跑到一半當掉，直接重跑就好，不會重複計算，也不會產生互相矛盾的結果。

4. 用小工具檢查大量輸出：管線

批次跑完有一堆資料夾。不寫程式，用 | 把小指令串起來就能快速檢查：前一個指令的輸出，變成下一個指令的輸入。

二例題（完整示範）

例題

已經跑過一次 batch.py（10 組）。現在在 GRID 加入 "noise": [0.05, 0.3] 再跑。預測：應該有幾組、第二次執行會跳過幾組、summary.csv 會有幾列？然後實際跑，比對預測。

步驟 1：先算。5 個振幅 × 2 個 seed × 2 個雜訊 = 20 組。直覺上，原本 noise = 0.05 的 10 組已經跑過，應該跳過 10 組、summary.csv 有 20 列。

步驟 2：實際跑。

項目預測實際
執行的組數1020（一組都沒跳過）
summary.csv 列數2030
noise = 0.05 的每組筆數24（重複）

步驟 3：找原因。資料夾名稱由參數組成，加了 noise 之後名稱從 s2_amp0.2_seed1 變成 s2_amp0.2_seed1_noise0.05，舊資料夾對不上，所以全部重跑。而 collect() 會讀 runs/ 底下所有資料夾，舊的 10 個也被收進來，noise = 0.05 的結果因此出現兩次。

步驟 4：判斷影響，下結論。這次重複的兩份數值剛好一樣，所以平均值沒變；但筆數、標準差都錯了。如果舊結果是用不同的預設值跑的，平均值也會悄悄被拉偏，而且程式不會報錯。修正方式：彙整時只收「這次網格裡的組合」，或每次換網格前清空 runs/。

這個例題教的方法

批次結果出錯時通常不會報錯，只會「多一些」或「少一些」。習慣用簡單的數字先預測（應該幾組、幾列），再跟實際比對。數字對不上，就是線索。

Day 5變化 1：分離偏差來源

例題跑完後，noise = 0.3 在 S2 = 1.00 時的最小潮差約 1.12 m，理論是 0。用第 1 週例題的四步，把落差拆成「一天的時間窗」和「雜訊」兩個來源。

提示

加一組 --noise 0 當基準。雜訊為 0 時剩下的部分，就是時間窗造成的。

參考答案

雜訊 0 時約 0.31 m（時間窗），雜訊 0.05 時約 0.34–0.38 m，雜訊 0.3 時約 1.1 m。雜訊越大，每日最高與最低被往外推得越多，偏差隨雜訊快速增加。

變化 2：讓一組失敗，批次仍要跑完

在網格加入一組 s2_amp = -1。現在的 batch.py 會怎麼處理？讓它跑完其他組，最後列出失敗清單，並決定失敗的那組要不要出現在 summary.csv。

提示

submit() 已經回傳結束碼。失敗的那組不會產生 metrics.json，所以 collect() 不會收到它。問題是：你要不要在摘要裡明確記下「這組失敗了」？

變化 3：讓 AI 寫檢查腳本，再抓它的錯

請 AI 寫一支 check_summary.py：「讀 summary.csv，確認每組參數都有結果、沒有重複」。用例題那份 30 列的 summary 測試它。它抓得到重複嗎？抓不到的話，錯在哪一行？

提示

常見的錯：只檢查 run 欄位是否重複（資料夾名稱不同，所以抓不到），而沒有檢查「參數組合」是否重複。
