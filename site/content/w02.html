這週在練什麼

第 1 週改參數的方式是打開檔案改常數，再手動執行。做一次可以，做五十次就會出錯：忘了改回來、不記得這張圖是哪組參數跑的。

這週把程式改成「用參數呼叫」的工具，再寫一支批次腳本自動跑完一整組參數、彙整結果。這個介面是後面所有工程主題的共同起點：排程器、Docker 容器、REST API、MLOps 流程，本質上都是「用參數執行一支程式，檢查結束碼與輸出檔」。

對應職缺

職缺說「系統性的控制變數，結果不如預期就砍掉換方向」。批次工作讓控制變數變得便宜，這是做到這件事的前提。也是 Must Have 2「自有基礎建設」的最小版本。

範例程式：week02/tide_cli.py（一次實驗）與 week02/batch.py（一整組實驗）。練習題在 week02/exercises.md。

Day 1命令列參數與結束碼

argparse 把命令列上的文字轉成程式裡的變數。每個參數都有型別、預設值與說明，執行 --help 就能看到完整清單。

week02/tide_cli.py
p = argparse.ArgumentParser(description="合成潮位：M2 + S2 + 雜訊")
p.add_argument("--s2-amp", type=float, default=0.45, help="S2 振幅 [m]")
p.add_argument("--freq", default="h", help='取樣頻率，如 "h"、"30min"')
p.add_argument("--seed", type=int, default=42, help="亂數種子")
p.add_argument("--out", required=True, help="輸出資料夾")

參數不合理時，程式不該硬跑出一個奇怪的結果，而是明確地失敗：

week02/tide_cli.py
errors = validate(a)
if errors:
    for e in errors:
        print(f"參數錯誤：{e}", file=sys.stderr)   # 錯誤寫到 stderr
    return 2                                      # 非 0 = 失敗
名詞：結束碼（exit code）

程式結束時回報的數字。0 代表成功，非 0 代表失敗，慣例上 2 代表參數用錯。批次系統、排程器、CI 都只看這個數字判斷成敗，不會讀你印出來的文字。

輸出給誰看本範例放什麼
stdout（標準輸出）下一個程式一行 JSON 結果
stderr（標準錯誤）人錯誤訊息
結束碼呼叫它的程式0 成功、2 參數錯誤

Day 3批次的四個步驟

batch.py 做四件事。按「執行」看一次完整流程，再按一次看第二次執行有什麼不同。勾選「加入錯誤參數」看失敗如何被處理。

  1. 定義參數網格：GRID 寫要變的參數與取值，itertools.product 列出所有組合。
  2. 送出工作：每組參數用 subprocess.run 呼叫一次 tide_cli.py，檢查結束碼。
  3. 跳過已完成：結果已存在且設定相同就不重跑。
  4. 彙整：讀回每個資料夾的 config 與 metrics，合併成 summary.csv。
week02/batch.py
GRID = {
    "s2_amp": [0.20, 0.45, 0.70, 0.90, 1.00],
    "seed": [1, 2],
}

def already_done(folder: Path, params: dict) -> bool:
    """結果存在、且當時的設定跟這次相同，才算做過。"""
    cfg, met = folder / "config.json", folder / "metrics.json"
    if not (cfg.exists() and met.exists()):
        return False
    old = json.loads(cfg.read_text(encoding="utf-8"))
    return all(old.get(k) == v for k, v in params.items())
名詞：冪等性（idempotency）

做一次或做很多次，結果都一樣。批次跑到一半當掉，直接重跑就好，不會重複計算，也不會產生兩份互相矛盾的結果。第 12 週的 ETL、第 21 週的流程編排都要求這個性質。

為什麼要比對設定，而不只是檢查檔案存在

如果只看 metrics.json 在不在，你改了預設雜訊再重跑，舊結果會被當成新結果沿用，整份彙整悄悄混了兩種設定。比對 config 才能防住這種錯。

Day 4彙整與檢查：模擬和理論差在哪

summary.png 畫出每個 S2 振幅下的最大、最小每日潮差，疊上理論虛線 2(M2+S2) 與 2|M2−S2|。最大潮差幾乎貼著理論線，最小潮差在 S2 接近 M2 時卻明顯偏大。實際跑出來的數字：

S2 振幅模擬最小潮差（seed 1／2）理論 2|M2−S2|
0.451.12／1.16 m1.10 m
0.900.38／0.40 m0.20 m
1.000.34／0.34 m0.00 m

偏差有兩個來源，都在「每日最高減每日最低」這個算法本身，不是模型錯了：

  • 一天的時間窗：理論小潮潮差是包絡線最窄那一瞬間的值。但每日統計看的是整整 24 小時，前後 12 小時包絡線已經變寬，所以就算沒有雜訊，每日最小潮差也不會是 0。
  • 雜訊的極值：每天 24 筆各帶雜訊，最高那筆傾向被往上推，最低那筆被往下推，潮差系統性偏大。

小潮時真實潮差很小，這兩個偏差的比例就變得很明顯。要分辨哪個來源比較大，把 --noise 0 跑一次就知道。

Day 5Linux 基本操作：管線

批次跑完會產生一堆資料夾。不寫程式，用幾個小指令串起來就能快速檢查。關鍵是管線 |：把前一個指令的輸出，接成下一個指令的輸入。

指令做什麼
ls runs | wc -l數有幾個實驗資料夾
grep -h min_range runs/*/metrics.json一次列出所有結果的最小潮差
cat runs/*/config.json | grep seed | sort | uniq -c統計每個 seed 出現幾次
echo $?（PowerShell：$LASTEXITCODE）看上一個指令的結束碼

Windows 上用 Git Bash 或 WSL 執行。這些指令先自己查用法，不要讓 AI 直接給答案。第 15 週架 Linux 服務時，看日誌、找錯都靠這幾招。
