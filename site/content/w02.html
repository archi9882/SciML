第 1 週你一次改一個常數、手動跑、手動比較。這樣做五次還行，做五十次就會出錯：忘了改回來、不記得這張圖是哪組參數跑的、新舊結果混在一起。

為什麼要學這個

職缺說「系統性的控制變數，結果不如預期就砍掉換方向」。前提是「改一個參數、看結果」這件事要便宜而且不出錯。這週做的「用參數呼叫程式、批次執行、自動彙整」，也是之後排程、容器、API、MLOps 的共同起點：它們本質上都是用參數執行一支程式，再檢查結束碼與輸出檔。

這週在大圖裡屬於「ETL」與「部署與排程」兩格的最小版本。範例：week02/runoff_cli.py（一次實驗）、week02/batch.py（一整組實驗）。

一理論與示範

要讓實驗便宜又不出錯，需要四個觀念：用參數呼叫程式、用結束碼回報成敗、批次要能安全地重跑、用小工具快速檢查大量輸出。

Day 11. 一次執行＝一次實驗：參數與結束碼

argparse 把命令列上的文字轉成程式裡的變數，每個參數有型別、預設值與說明，--help 會列出全部。參數不合理時，程式要明確失敗，而不是硬算出一個怪結果。

week02/runoff_cli.py（節錄）
p.add_argument("--k-hours", type=float, default=1.2, help="退水常數 k [hr]（預設 1.2）")
p.add_argument("--freq", default="10min", help='取樣頻率，如 "10min"、"30min"')
p.add_argument("--out", required=True, help="輸出資料夾")

errors = validate(a)
if errors:
    for e in errors:
        print(f"參數錯誤：{e}", file=sys.stderr)   # 錯誤寫到 stderr
    return 2                                      # 非 0 = 失敗
名詞：結束碼（exit code）

程式結束時回報的數字。0 是成功，非 0 是失敗，慣例上 2 代表參數用錯。批次系統、排程器、CI 只看這個數字，不會讀你印出來的文字。

輸出給誰看本範例放什麼
stdout下一個程式一行 JSON 結果
stderr人錯誤訊息
結束碼呼叫它的程式0 成功、2 參數錯誤
輸出資料夾三個月後的你config.json、metrics.json、flow.csv

Day 22. 第 1 週的單位陷阱在這裡修好

runoff_cli.py 從時間軸算出每一步的實際小時數，並用結束時間決定筆數，不再寫死每步 600 秒與 days * 144。打開下方的「步長用實際取樣間隔」，兩種頻率的退水都會落在合理的位置。

time = pd.date_range(start=a.start, end=pd.Timestamp(a.start) + pd.Timedelta(days=a.days),
                     freq=a.freq, inclusive="left")
dt_h = step_hours(a.freq)                              # 每一步實際幾小時
t_hours = (time - time[0]) / pd.Timedelta(hours=1)   # 雨量依實際經過的小時數產生

--freq 10min 得到 8640 筆、洪峰 116.9 m³/s、退水檢查 0.351；--freq 30min 得到 2880 筆、洪峰 123.6 m³/s、退水檢查 0.340。筆數剛好差 3 倍，洪峰差約 6%，來自步長不同；步長越大，歐拉的退水誤差越大（0.340 離理論 0.368 比 0.351 更遠）。修正成立。

Day 33. 批次的四個步驟，以及為什麼要能安全重跑

batch.py 做四件事：定義參數網格、每組送出一個工作並檢查結束碼、跳過已完成的、讀回所有結果彙整成 summary.csv。按「執行」看一次，再按一次看第二次有什麼不同。

week02/batch.py
GRID = {
    "k_hours": [0.4, 0.8, 1.2, 2.4, 4.8],
    "seed": [1, 2],
}

def already_done(folder: Path, params: dict) -> bool:
    cfg, met = folder / "config.json", folder / "metrics.json"
    if not (cfg.exists() and met.exists()):
        return False
    old = json.loads(cfg.read_text(encoding="utf-8"))
    return all(old.get(k) == v for k, v in params.items())
名詞：冪等性（idempotency）

做一次或做很多次，結果都一樣。批次跑到一半當掉，直接重跑就好，不會重複計算，也不會產生互相矛盾的結果。

4. 用小工具檢查大量輸出：管線

批次跑完有一堆資料夾。不寫程式，用 | 把小指令串起來就能快速檢查：前一個指令的輸出，變成下一個指令的輸入。

例題筆記 Day 4・Q1

已經跑過一次 batch.py（10 組）。現在在 GRID 加入 "noise": [0.08, 0.2] 再跑。預測：應該有幾組、第二次執行會跳過幾組、summary.csv 會有幾列？然後實際跑，比對預測。

步驟 1：先算。5 個 \(k\) × 2 個 seed × 2 個雜訊 = 20 組。直覺上，原本沒有 noise 維度的 10 組用的是預設值 0.08，等於 noise = 0.08 的 10 組已經跑過，應該跳過 10 組、summary.csv 有 20 列。

步驟 2：實際跑。

項目預測實際
執行的組數1020（一組都沒跳過）
summary.csv 列數2030
noise = 0.08 的每組筆數24（重複）

步驟 3：找原因。資料夾名稱由參數組成，加了 noise 之後名稱從 k_hours0.4_seed1 變成 k_hours0.4_seed1_noise0.08，舊資料夾對不上，所以全部重跑。而 collect() 會讀 runs/ 底下所有資料夾，舊的 10 個也被收進來，noise = 0.08 的結果因此出現兩次。

步驟 4：判斷影響，下結論。這次重複的兩份數值剛好一樣，所以平均值沒變；但筆數、標準差都錯了。如果舊結果是用不同的預設值跑的，平均值也會悄悄被拉偏，而且程式不會報錯。修正方式：彙整時只收「這次網格裡的組合」，或每次換網格前清空 runs/。

這個例題教的方法

批次結果出錯時通常不會報錯，只會「多一些」或「少一些」。習慣用簡單的數字先預測（應該幾組、幾列），再跟實際比對。數字對不上，就是線索。

Day 5變化 1：分離偏差來源筆記 Day 5・Q1

例題跑完後，預設參數下，觀測洪峰 130.9 m³/s，模型洪峰 116.9 m³/s，差了 14 m³/s（+12%）。用第 1 週例題的四步，說明這個落差從哪來，並預測 --noise 0.2 時會是多少。

提示

加一組 --noise 0 當基準。雜訊為 0 時，觀測與模型的洪峰會一樣。

參考答案

雜訊 0 時兩者相同（116.9）；雜訊 8% 時 130.9（+12%）；雜訊 20% 時 156.7（+34%）。流量計的誤差是乘性的，洪峰附近流量大，絕對誤差也大；整段資料取最大值，等於挑出被誤差往上推得最多的那一筆，所以洪峰系統性偏高，偏差隨雜訊快速增加。
