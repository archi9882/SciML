# pyflow 設計文件

日期：2026-10-28
狀態：第一版 demo 已實作（見本資料夾外的程式碼）。本文記錄定稿的決策與理由。

## 1. 目標

使用者把任意 .py 檔拖曳進網頁，在搜尋欄輸入變數或函式名稱，即以圖形顯示其前後傳遞關係。
作品公開在 GitHub，訪客不需安裝即可試用。

## 3. 圖的資料模型

節點 id 規則：

- `fn:<qualname>`：函式、方法、類別（例：`fn:Cart.add`）；模組層級程式碼為 `fn:<module>`
- `var:<scope>:<name>`：變數與參數（例：`var:main:data`）；同名不同作用域即為不同節點
- `ext:<dotted name>`：外部呼叫（例：`ext:np.mean`）

邊的種類：

| kind | 家族 | 方向 |
|---|---|---|
| call | 呼叫 | 呼叫者 -> 被呼叫者 |
| assign | 資料 | 來源變數 -> 目標變數 |
| arg | 資料 | 引數 -> 參數，或引數 -> 外部呼叫 |
| return | 資料 | 變數 -> 所屬函式 |
| result | 資料 | 函式 -> 接收回傳值的變數或參數 |

關鍵設計：

1. **外部節點只進不出。** `y = len(x)` 畫成 `x -> len`（引數）與 `x -> y`（穿透），
   而不是 `x -> len -> y`；否則所有用到 `len` 的變數會被錯誤地連在一起。
2. **鄰域走訪不跨家族。** 經由資料流抵達的函式（代表它的回傳值），不再沿呼叫邊展開；
   反之亦然。否則查一個變數會牽出所有呼叫者。
3. **兩階段分析。** 先建立作用域並收集每個作用域綁定的名稱（Python 在編譯期決定區域變數），
   再依序走訪敘述產生邊。

## 4. 與交接文件不同的判斷（實作時決定）

- **全域與閉包變數的「讀取」有連線。** 交接文件建議全域變數標示為未支援。實作時發現讀取模組常數
  （如 `STOP_WORDS`）非常常見，標示為未支援會產生大量雜訊，且讀取的解析是確定的。
  因此改為：讀取會連到外層變數；只有透過 `global`／`nonlocal` 重新綁定時才列為未分析。
- **方法呼叫的簡易型別推論。** `cart = Cart(...)` 或參數註記 `p: Product` 時，
  `cart.add()` 會解析到 `Cart.add`。（第二輪起也追蹤同檔案內的繼承，見 4.1）
- **dataclass 建構子。** 沒有 `__init__` 的類別，以有型別註記的類別屬性作為建構子參數。

## 4.1 第二輪打磨（2026-10-29）

使用者要求四個方向都達到滿意：視覺質感、互動與程式碼對照、大檔案可讀性、分析能力。

| 方向 | 做法 |
|---|---|
| 分析能力 | `self.x` 屬性成為節點（與 dataclass 欄位共用）；同檔案內的繼承與 `super()`；`append`／`update` 等就地修改流入容器 |
| 互動 | 滑過節點高亮它到中心的路徑並顯示說明；點原始碼某行跳到該行的名稱；原始碼用 Python `tokenize` 上色並標示目前圖涉及的行 |
| 大檔案 | 總覽超過 60 個節點時把方法收合進類別；不相連的部分依螢幕比例排成多列；縮放下限 0.6；節點過多時提示 |
| 視覺 | IBM Plex 字體、重新置中時的過場動畫、邊的標籤只在小圖或路徑上顯示 |
| 執行 | 所有函式庫改由 `scripts/vendor.py` 下載並驗證雜湊，網站不再依賴 CDN，可離線使用 |

實作時的判斷：

- **類別框只在不誤導時畫出。** dagre 的群組排版偶爾會把非成員節點排進框內；
  遇到這種情況就拆掉該框，改用 `Cart.add()` 這類完整名稱，不讓框宣稱錯誤的歸屬。
- **窄螢幕改為由上而下。** 「由左至右」是桌面版的約定；手機直向寬度不足，圖寬度小於 600px 時改成由上而下。

## 4.2 第三輪：改為單一問題「改了會影響哪裡」（2026-11-04）

使用者要求作品能達到 GitHub 熱門與 VS Code Marketplace 上架的水準，且只回答一個問題：
使用者關心的某個變數如果改變，哪裡會出現變化。

| 決定 | 理由 |
|---|---|
| 以 `impact()` 為產品核心，網頁預設進入「會影響哪裡」模式 | 單一明確的問題比通用的圖更容易被理解與推薦 |
| 新增 `control` 邊（if／while／for／match／守衛式提前返回） | 只看資料流會漏掉 `if x: y = 1` 這類真實的影響；以 `influence: "condition"` 另外標示，可關閉，因為證據較弱 |
| 路徑成本先比「經過幾個條件」再比步數 | 有純資料路徑時一律以資料路徑說明 |
| 物件取決於建構子引數 | `c = Child(n)` 中 `c` 的狀態來自 `n`；先前只連到類別節點會漏掉 |
| 以「建構呼叫」而非「來源只有一個類別」判斷實例 | 後者會把 `len(Cart())` 誤判為 `Cart` |
| 外部呼叫分「輸出／副作用」與一般函式庫呼叫（名稱啟發式） | 使用者最在意的是「會不會改變輸出」；啟發式不完美，因此只用於分類，不影響是否列出 |
| `refs` 以 UTF-16 欄位輸出 | 編輯器與 JavaScript 都以 UTF-16 計算欄位；`ast` 的 UTF-8 位元組偏移在中文或 emoji 之後會對不上 |
| 擴充套件透過 `python -I -c` 啟動隨附的分析器，原始碼走 stdin | 不需安裝套件、不受使用者環境變數影響、未儲存的修改也能分析、程式碼不離開本機 |
| 編輯後立即清除標記，不嘗試平移 | 位置過期的標記比沒有標記更誤導 |
| 結果過大時，圖只畫最近的 150 個，超過 40 個改畫樹；清單與標記涵蓋全部 | 數百個節點的圖無法閱讀，但答案不能因此被截斷 |

競品調查（簡短，非窮盡）：JetBrains 的 IntelliJ 系列有「Data Flow from Here」，但 PyCharm 的 Python 支援在我查到的資料中
仍是功能請求（PY-32296）；VS Code Marketplace 上我找到的最接近者是以符號層級分析依賴影響的工具，沒有找到 Python 變數層級的資料流影響工具。

## 5. 已知限制

見 README 的「Limits」章節：單檔、不區分呼叫情境、每個屬性一個節點（不區分物件）、不追蹤別名、控制流程不畫成資料流、不追蹤其他檔案的基底類別。
